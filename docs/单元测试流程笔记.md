# C++ JSON 解析器单元测试流程笔记

本文记录本项目的单元测试配置方案与使用流程，适用于为 `value.hpp`（以及后续 `lexer/parser/serializer`）编写单元测试。

## 一、测试方案总览

| 项目 | 选型 | 说明 |
| --- | --- | --- |
| 测试框架 | GoogleTest | 通过 CMake FetchContent 在线拉取，无需本地安装 |
| 测试注册 | CTest | 根 CMakeLists 用 `include(CTest)` 开启 |
| 开关 | `BUILD_TESTING` | CMakePresets.json 的 base 预设已设为 `ON` |
| 断言风格 | `EXPECT_*` / `ASSERT_*` | 失败不中断 / 失败立即中止 |

整体结构分两层：

1. **根 `CMakeLists.txt`**：负责开关测试（`BUILD_TESTING`）并引入 `tests/` 子目录
2. **`tests/CMakeLists.txt`**：负责拉取 GoogleTest、定义每个测试可执行文件并注册到 CTest

> 补充：除 GoogleTest 外，`tests/standalone/` 还提供"手写 main 测试"（不依赖任何第三方框架），见第七节。

## 二、根 CMakeLists.txt 配置

在根目录 `CMakeLists.txt` 末尾（`my-json` 可执行目标之后）追加：

```cmake
# ============================================================
# 单元测试
# ============================================================

# include(CTest) 会定义 BUILD_TESTING 选项（默认 ON），并自动调用 enable_testing()
include(CTest)

if(BUILD_TESTING)
    add_subdirectory(tests)
endif()
```

要点：

- `include(CTest)` 定义 `BUILD_TESTING` 缓存变量，默认 `ON`，可通过 `-DBUILD_TESTING=OFF` 关闭
- 关闭测试时整个 `tests/` 目录都不参与构建，不会拖慢编译

## 三、tests/CMakeLists.txt 配置

```cmake
# ============================================================
# 测试框架：GoogleTest（FetchContent 在线拉取）
# ============================================================
include(FetchContent)

FetchContent_Declare(
    googletest
    URL https://github.com/google/googletest/archive/refs/tags/v1.14.0.zip
)
FetchContent_MakeAvailable(googletest)

# ============================================================
# 测试目标：JsonValue
# ============================================================

# value.hpp 是 header-only，但链接 json-parser 后会自动获得
# include 目录（PUBLIC 传递）和 C++17 标准，后续测试 lexer/parser 也直接复用
add_executable(test_json_value test_json_value.cpp)

target_link_libraries(test_json_value PRIVATE
    json-parser
    GTest::gtest_main   # 提供 main()，测试文件里不用自己写
)

# ============================================================
# 注册到 CTest
# ============================================================

# 方式一（推荐）：自动发现每个 TEST 用例，ctest 里能看到每个用例的通过/失败
include(GoogleTest)
gtest_discover_tests(test_json_value)

# 方式二（更简单）：每个测试可执行文件注册为一条测试
# add_test(NAME test_json_value COMMAND test_json_value)
```

## 四、测试代码编写规范

### 1. 基本骨架

测试文件包含被测头文件与 gtest 头文件，**不需要自己写 main()**（由 `gtest_main` 提供）：

```cpp
#include "value.hpp"
#include <gtest/gtest.h>

TEST(JsonValueTest, DefaultIsNull) {
    JsonValue v;
    EXPECT_TRUE(v.isNull());
    EXPECT_EQ(v.type(), JsonType::Null);
}
```

`TEST(Suite, Case)` 两个参数含义：

- `Suite`：测试套件名（按被测模块/类分组，如 `JsonValueTest`、`LexerTest`）
- `Case`：具体用例名（描述该用例验证什么行为，如 `DefaultIsNull`）

### 2. 断言选择

| 断言 | 含义 |
| --- | --- |
| `EXPECT_TRUE(x)` / `EXPECT_FALSE(x)` | 布尔断言，失败后继续跑 |
| `EXPECT_EQ(a, b)` / `EXPECT_NE(a, b)` | 相等 / 不相等，失败后继续跑 |
| `EXPECT_DOUBLE_EQ(a, b)` | 浮点比较（避免二进制精度误差） |
| `EXPECT_THROW(expr, ExceptionType)` | 断言抛出指定异常 |
| `EXPECT_NO_THROW(expr)` | 断言不抛异常 |
| `ASSERT_*` 系列 | 同 `EXPECT_*`，但失败后**立即中止**当前用例，适合后续步骤依赖前一步结果的场景 |

浮点数注意：JSON 数字统一存 `double`，比较时应使用 `EXPECT_DOUBLE_EQ` 而非 `EXPECT_EQ`。

### 3. 异常用例写法

```cpp
TEST(JsonValueTest, AsNumberThrowsOnWrongType) {
    JsonValue v(true);  // 存的是 Bool
    EXPECT_THROW(v.asNumber(), JsonValueException);
}

TEST(JsonValueTest, AtThrowsOnOutOfRange) {
    JsonValue v(JsonValue(std::vector<JsonValue>{}));  // 空数组
    EXPECT_THROW(v.at(0), JsonValueException);
}
```

## 五、构建与运行

### 1. 配置、构建、运行一条龙

```powershell
# 配置（preset 里 BUILD_TESTING 已默认 ON）
cmake --preset gcc-debug

# 构建
cmake --build build/gcc-debug

# 运行全部测试
ctest --preset gcc-debug
```

### 2. 只运行指定测试

```powershell
# 按测试二进制名过滤
ctest --test-dir build/gcc-debug -R test_json_value --output-on-failure

# 直接运行二进制，可加 gtest 过滤参数（支持通配符）
./build/gcc-debug/tests/test_json_value --gtest_filter=JsonValueTest.*
```

### 3. 查看测试列表

```powershell
./build/gcc-debug/tests/test_json_value --gtest_list_tests
```

## 六、常见问题与注意事项

### 1. 两种注册方式的取舍

- `gtest_discover_tests`：构建时会执行一次测试程序自动枚举用例，`ctest` 输出按**用例粒度**展示，每个 TEST 独立统计通过/失败；代价是构建阶段会多跑一次程序
- `add_test`：每个测试二进制只注册一条记录，输出只有整体通过/失败，简单可靠
- 建议：用例数量不多时用 `add_test` 即可，用例多了再切换 `gtest_discover_tests`

### 2. 网络问题

FetchContent 会从 GitHub 拉取 GoogleTest，国内网络可能慢或失败。备选方案：

- 换成镜像地址：`https://gitee.com/mirrors/googletest`
- 提前下载源码到本地，改用 `SOURCE_DIR` 指定本地路径

### 3. 新增测试文件

后续为 lexer / parser 写测试时，每个模块新建一个测试 cpp，并在 `tests/CMakeLists.txt` 中重复「定义可执行文件 + 链接 + 注册」三件套。也可用 `file(GLOB ...)` 自动收集，但推荐显式列举，构建更可控。

### 4. include 路径来源

测试文件直接 `#include "value.hpp"` 即可，因为链接 `json-parser` 时其 PUBLIC 的 `include/` 目录会自动传递给测试目标，无需额外配置 include 路径。

### 5. 警告策略

根工程对库本身开了 `-Werror / /WX`，但该选项是 `PRIVATE`，不会污染 GoogleTest 与测试目标，测试代码目前不受严格警告约束。如需对测试代码同样强制规范，可后续单独给测试目标配置编译选项。

### 6. clangd 报 `'gtest/gtest.h' file not found`

**现象**：IDE 中测试文件飘红提示找不到 gtest 头文件（`pp_file_not_found`），但命令行 `cmake --build` 编译正常。

**原因**：clangd 依靠编译数据库 `compile_commands.json` 获取每个源文件的 include 路径。该文件生成在构建目录内（如 `build/clang-debug/`），clangd 默认只在项目根附近查找，找不到就退回 fallback 模式——不带任何 `-I` 参数，gtest 头文件自然全部解析失败。

**解决**：项目根已由 CMake 自动生成 `.clangd`，内容指向当前构建目录：

```yaml
CompileFlags:
  CompilationDatabase: build/clang-debug
```

使用要点：

- `.clangd` 是根 `CMakeLists.txt` 在 configure 阶段自动生成的（已加入 `.gitignore`），**不要手动修改**，否则下次 configure 会被覆盖
- **切换预设后需重新 configure**（如 `cmake --preset gcc-debug`），`.clangd` 才会指向新构建目录下的编译数据库
- 修改 `.clangd` 或切换预设后，需重启 clangd 才生效（VS Code 命令面板执行 "clangd: Restart language server"，或重载窗口）

排查提示：若改完仍报错，可在终端用 clangd 自检定位问题：

```powershell
# 应能看到 "Loaded compilation database from .../compile_commands.json"
clangd --check=tests/test_json_value.cpp
```

若输出 `Failed to find compilation database`，说明 `.clangd` 路径指向不对，检查 `CompilationDatabase` 是否为当前预设的构建目录。
